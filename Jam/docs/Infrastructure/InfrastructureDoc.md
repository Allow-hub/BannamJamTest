# Infrastructure層の設計
Infrastructure層は **外部APIと他層へのアダプター的役割** を持つ  
Domain層やUseCase層が外部ライブラリ（Siv3Dや物理エンジン）に依存しないように橋渡しを行う

## メリット
- 外部システムへの依存を局所化できる
- 外部ライブラリや技術の変更が他層に影響しにくい
- テストが容易になる（モックに置き換えやすい）

## Infrastructure層の各種サービスおよびユーティリティ

## Infrastructure層のモジュール

### AudioLoader.h
- **役割:** 音声ファイル（BGM、SEなど）のロードと管理を行う。ファイルパスからSiv3DなどのオーディオAPIに適した形式で読み込む。
- **メリット:** オーディオリソースのロード処理を抽象化し、特定のファイル形式やライブラリへの依存を隠蔽できる。
- **デメリット:**
- **制作者:** Allow-hub

### EnemyLoader.h
- **役割:** 敵キャラクターのデータ（設定、アニメーション情報など）を外部からロードする。
- **メリット:** 敵データのロード処理をカプセル化し、データ形式の変更が他の層に影響しないようにする。
- **デメリット:**
- **制作者:** Allow-hub

### FactoryServiceLocator.h
- **役割:** サービスやファクトリのインスタンスを提供するロケータパターンを実装。必要なサービスを動的に解決できる。
- **メリット:** 依存性の解決を一元化し、システムの柔軟性と拡張性を高める。
- **デメリット:** 依存関係が隠蔽され、コードの追跡が難しくなる可能性がある。
- **制作者:** Allow-hub

### GridRenderer.h
- **役割:** グリッド描画に関する低レベルなレンダリング機能を提供。Siv3Dなどの描画APIを使用してグリッドを画面に描画する。
- **メリット:** グリッド描画の詳細をカプセル化し、描画ロジックの再利用性を高める。
- **デメリット:**
- **制作者:** Allow-hub

### IndependentObjectFactory.h
- **役割:** 独立したゲームオブジェクト（例:飛び道具）を生成するファクトリを提供する。
- **メリット:** オブジェクトの生成ロジックを一元化し、複雑な初期化処理を抽象化する。
- **デメリット:**
- **制作者:** Allow-hub

### IPhysicsBodyFactory.h
- **役割:** 物理ボディを生成するためのインターフェースを定義し、特定の物理エンジンへの依存を抽象化する。
- **メリット:** 物理エンジンの選択肢を増やし、交換可能性を高める。
- **デメリット:**
- **制作者:** Allow-hub

### PhysicsConverter.h
- **役割:** 
  - Domain層の `PhysicsMaterial` を Siv3D の `P2Material` に変換
  - Player のステータスを JSON からロードする関数も提供
- **メリット:** 
  - Domain層は物理APIの型を知らずに済む
  - JSONロードなどの外部依存処理をまとめて管理できる
- **デメリット:**
- **制作者:** Allow-hub

### PhysicsFilterManager.h
- **役割:** 物理エンジンの衝突フィルター設定を管理する。どのオブジェクトがどのオブジェクトと衝突するかを定義。
- **メリット:** 衝突判定のロジックを一元化し、柔軟な物理シミュレーションを実現。
- **デメリット:**
- **制作者:** Allow-hub

### Siv3DAudio.h
- **役割:** Siv3Dフレームワークのオーディオ機能を直接利用するためのインターフェースを提供する。
- **メリット:** 既存のオーディオAPIとの直接的な連携が可能。
- **デメリット:** Siv3Dへの強い依存を生み出す。
- **制作者:** Allow-hub

### Siv3DCursorUtil.h
- **役割:** Siv3Dフレームワークのカーソル（マウスカーソルなど）操作に関するユーティリティ機能を提供する。
- **メリット:** カーソル表示や位置取得などの共通処理を簡素化する。
- **デメリット:** Siv3Dへの強い依存を生み出す。
- **制作者:** Allow-hub

### Siv3DInputManager.h
- **役割**：
  - Siv3D の入力 (`Input` クラス) を Domain層の `IInputService` に適合させるアダプター
- **メリット**：
  - Domain層や UseCase層は Siv3D の API を直接呼ばない
  - 入力ライブラリを変更しても Domain層に影響を与えない
- **デメリット:** Siv3Dへの強い依存を生み出す。→Infrastructure層で閉じ込めることで解決
- **制作者:** Allow-hub

### Siv3DPhysicsBody.h
- **役割**：
  - Domain層の `IPhysicsBody` と Siv3D の物理エンジンを適合させる
  - 当たり判定のイベント通知も担当（`ICollisionListener` に通知）
- **メリット**：
  - Domain層のオブジェクトはどの物理エンジンを使っているか知らない
  - 物理の処理や衝突判定を Infrastructure層に委譲できる
- **デメリット:** Siv3Dへの強い依存を生み出す。
- **制作者:** Allow-hub

### Siv3DPhysicsBodyFactory.h
- **役割:** Siv3Dフレームワークの物理エンジンに適した物理ボディを生成するファクトリを提供する。IPhysicsBodyFactory.h の実装。
- **メリット:** Siv3Dの物理ボディ生成ロジックを一元化する。
- **デメリット:** Siv3Dへの強い依存を生み出す。
- **制作者:** Allow-hub

### StageFactory.h
- **役割:** ステージオブジェクトを生成するファクトリを提供する。
- **メリット:** ステージの生成ロジックを一元化し、複雑な初期化処理を抽象化する。
- **デメリット:**
- **制作者:** Wine-5

### StageLoader.h
- **役割:** ステージデータ（レイアウト、オブジェクト配置など）を外部からロードする。
- **メリット:** ステージデータのロード処理をカプセル化し、データ形式の変更が他の層に影響しないようにする。
- **デメリット:**
- **制作者:** Wine-5

### TextureLoader.h
- **役割:** テクスチャファイル（画像）のロードと管理を行う。ファイルパスからSiv3Dなどの画像APIに適した形式で読み込む。
- **メリット:** テクスチャリソースのロード処理を抽象化し、特定のファイル形式やライブラリへの依存を隠蔽する。
- **デメリット:**
- **制作者:** Wine-5
